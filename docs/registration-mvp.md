# Регистрация Место: реализованный сценарий

Дата: 2026-10-07. Этот документ заменяет прежнюю цепочку регистрации через SMS.

## Пользовательский сценарий

Обе роли проходят одинаковую последовательность: форма → письмо с шестизначным кодом → подтверждение email → создание аккаунта → окно входа с пустым полем пароля. Автоматического входа нет. Пароль задаётся в первой форме, не отправляется письмом и принимается при обычном входе.

Поля соискателя: имя (до 100 символов), email, пароль (от 8 символов, до 72 байт для bcrypt), согласие на обработку персональных данных. Работодатель дополнительно выбирает company / entrepreneur / private и указывает публичное название (до 150 символов). Поля перенесены из __HH__/html/index.html. Один email соответствует одному аккаунту с одной ролью.

Существующие кабинеты, вакансии, резюме и оценочные задания остаются прототипом; эта работа подключает регистрацию и парольный вход, а не превращает все кабинеты в готовые серверные приложения.

## Владелец каждого действия

| Компонент | Ответственность |
|---|---|
| web-service | Twig-формы, CSRF, браузерная сессия, безопасная передача IP, отображение ошибок и ожидания |
| verification-service | Заявка, валидация данных, ограничения, код, подтверждение, отмена, сохраняемая очередь |
| auth-service | Уникальный аккаунт, хеш пароля, единственная роль, создание пользователя, вход и токены |
| dictionaries-service | application_settings: сроки, число попыток, паузы, лимиты |
| event-api-service | Приём события отправки письма; ответ об успехе только после подтверждения Kafka |
| event-worker-service | Доставка события из Kafka в email-service, повторы обработки; код не попадает в журналы |
| email-service | Сохранение события по event_id, письмо и технические повторы того же сообщения |
| ONMI_infra | Переменные окружения, маршруты, фоновые обработчики и локальный стек |

Browser → web → verification и verification → dictionaries работают через HTTP. Создание аккаунта выполняется защищённым внутренним HTTP-запросом verification → auth. Письма отправляются через HTTP event gateway → Kafka → event worker → email. Хеш пароля не публикуется в Kafka.

Внутренние адреса: AUTH_SERVICE_URL=http://nginx/auth, VERIFICATION_SERVICE_URL=http://nginx/api/registration, DICTIONARY_SERVICE_URL=http://nginx/api/refbook. Разрешены только настроенные адреса, редиректы POST отключены.

## API и состояния

Браузер использует POST /registration/start, /verify, /resend, /cancel, /status, /login. Каждый запрос требует X-CSRF-Token из страницы. web-service выделяет UUID до отправки запроса и сохраняет его в сессии: повтор при потерянном ответе не создаёт ещё одну заявку. В последующих действиях requestId берётся из серверной сессии; переданный браузером идентификатор другой заявки игнорируется.

verification-service сохраняет прежние имена /quick-signup, /check-code-email, /resend-code-email и добавляет /cancel, /status. Все пять маршрутов доступны через доверенный web-service. У прежних SMS-контроллеров, /verify, создания пользователя со случайным паролем и выдачи первого токена по одному UUID сняты маршруты.

Состояния: pending → creating → ready. Возможны cancelled, expired, conflict. Код подтверждает email только в pending. Повтор подтверждения creating/ready возвращает текущее состояние. Пока auth недоступен, creating остаётся сохранённым; UI опрашивает status. ready появляется только после успешного создания аккаунта в auth.

## Сроки и ограничения

- Заявка живёт 600 секунд от создания. Повторная отправка не сдвигает expires_at.
- Код живёт не более 300 секунд и не дольше заявки; возможное округление уменьшает срок, не увеличивает его.
- Пять неверных вводов блокируют текущий код. Счётчик неверных попыток фиксируется даже при ответе с ошибкой.
- Ручная повторная отправка доступна через 60 секунд. Максимум три дополнительных генерации. Предыдущий код аннулируется, счётчик ввода сбрасывается.
- Технический повтор доставки сохраняет код и event_id, не расходует лимит ручных генераций.
- Отмена аннулирует код и невыполненные отправки. Новая форма создаёт новый requestId; email-пауза остаётся действующей.
- На email новая регистрация возможна не чаще раза в 60 секунд. Действующая заявка требует продолжения или отмены.
- С одного IP максимум пять заявок за 60 секунд. Подсчёт и создание защищены транзакционной advisory-блокировкой. Отменённые заявки учитываются.
- Подтверждённая заявка продолжает создание аккаунта после 600 секунд. Отменить подтверждённую заявку нельзя.

Состояние кода и счётчик хранятся в PostgreSQL вместе с заявкой и изменяются под блокировкой строки. Это устраняет разрыв между Redis и PostgreSQL при подтверждении, отмене и генерации. Старые company/SMS-модули и Redis-хранилища регистрации verification-service удалены 8 октября 2026. Код хранится как HMAC, постоянный пароль — только как bcrypt-хеш. В outbox код присутствует лишь в ожидающем отправки письме; обработанные payload очищаются.

## Восстановление и безопасность

Изменение заявки и создание задания registration_outbox выполняются одной транзакцией. app:registration:dispatch повторяет невыполненные задания с задержкой до 60 секунд, в Compose запускается каждые две секунды. Порядок блокировок одинаков: сначала заявка, затем задание. Истёкшие/отменённые и заменённые отправки становятся obsolete. Неопределённый результат отправки повторяется с тем же event_id; email-service устраняет дубли событий. SMTP не гарантирует строго однократную доставку: при сбое после принятия письма сервером повтор может доставить такое же письмо ещё раз.

Auth создаёт аккаунт с user_uuid=requestId и уникальным lower(email). Повтор того же создания возвращает ready и не меняет пароль. Конфликт с другим аккаунтом становится conflict; UI предлагает обычный вход. После завершения хеш удаляется из заявки и outbox, оставаясь в auth.users.

REGISTRATION_INTERNAL_TOKEN — отдельный секрет verification → auth, минимум 32 случайных символа. WEB_SERVICE_INTERNAL_TOKEN используется для доверенного IP и HTTP регистрации из web. Пустые секреты закрывают внутренние действия. Секреты лежат только в игнорируемых .env. Регистрация не доверяет IP-заголовкам браузера. Сессия хранится в web-service/var/sessions, cookie HttpOnly/SameSite=Lax; токены авторизации остаются в серверной сессии. Для внешнего размещения нужны HTTPS, APP_ENV=prod и APP_DEBUG=0.

## Локальный запуск

Из ONMI_infra:

```sh
make registration-up
```

Сайт: http://localhost:8080. Локальный почтовый ящик: http://localhost:8025. Оба адреса привязаны к loopback. Письма локального режима попадают в Mailpit, а не на реальные внешние адреса.

registration-up устанавливает PHP-зависимости из composer.lock и создаёт отсутствующие .env из .env.example; значения Docker имеют приоритет. Перед первым запуском нужно подготовить ONMI_infra/.env из шаблона и локальные JWT-ключи.

registration-up использует проект mesto-web и дополняет прежний минимальный web-up. PostgreSQL использует отдельный именованный том registration_data; старый каталог storage/postgresql не изменяется. Миграции применены именно к этой локальной базе. Повторный запуск не очищает данные. Остановка — make registration-down (без удаления тома). Nginx использует Docker DNS для обновления адресов пересозданных сервисов; registration-up ожидает готовность контейнеров и перезагружает конфигурацию шлюза.

Для обычного полного стека перед включением сценария применить новые миграции auth/verification/dictionaries, затем обновить сервисы и кеш. make web-up является псевдонимом make registration-up и запускает весь локальный стек регистрации. Не запускайте одновременно минимальный и полный режимы одного compose-проекта с разными наборами сервисов.

## Проверки

- services/verification-service/tests/registration-contract.php: реальные миграции PostgreSQL, поля и обе роли, исходный пароль, попытки, код/заявка, отмена, ручные/технические повторы, восстановление после сбоя auth, завершение после срока, идемпотентность, одновременные отправки и восемь параллельных заявок по одному IP.
- services/web-service/tests/registration-e2e.py: реальный localhost → web → verification → event gateway → Kafka → worker → email → Mailpit → подтверждение → auth → вход с исходным паролем. Проверены обе роли, CSRF, привязка сессии, повторное подтверждение, /auth/user/me без старой связи компании, выход и отсутствие автоматической выдачи токенов браузеру.
- services/verification-service/tests/client-ip-contract.php и registration-settings.php: передача IP и согласованные значения настроек. Ручные повторные отправки проверяет registration-contract.php.
- Проверены PHP-синтаксис, контейнеры DI, Twig и синтаксис auth.js; Java-сервисы собраны.

Воспроизводимая проверка ограничений: из ONMI_infra выполнить `make registration-test`. Она создаёт одноразовый PostgreSQL и автоматически удаляет их. Сквозной тест: `python3 services/web-service/tests/registration-e2e.py` из корня при работающем локальном стеке.

Контрактные тесты выполнять только в одноразовом PostgreSQL, не в рабочей базе: они создают и очищают схемы с тестовыми именами. Сквозной тест создаёт тестовые аккаунты с адресами example.invalid в отдельном локальном стеке.
